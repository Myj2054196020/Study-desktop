# 工作经验沉淀 —— Study desktop（深夜书房 × 小咕）

> 本文沉淀本项目协作过程中的经验与教训，供后续迭代参考。作者：溪浣涟辞（产品作者）+ Codex（开发伙伴）。

## 一、产品理念（为什么这么做）

1. **定位是"学习工作台 / 学习助手"，不是工具集合**：功能可以多，但必须围绕"帮用户把学习变成习惯"展开，不做与定位绑定的单一卖点（如社交、排行榜）。
2. **迭代方式是"审视缺陷"而非"堆功能"**：每个版本先找产品缺陷与用户痛点，讨论方案后再动手，避免功能越加越臃肿。
3. **品牌一致性**：深夜书房 × 小咕（猫头鹰吉祥物）贯穿全站；台灯 = 专注的视觉母题；中文衬线标题、浅米色 + 琥珀暖色配色；动效签名"小咕跳"（spring 缓动）。
4. **本土化而非生搬硬套**：借鉴优秀产品时，先理解其设计逻辑，再结合本项目定位落地。

## 二、协作模式（重讨论，不迎合）

- 用户是产品作者，对方向有最终决定权；Codex 提供专业判断与可执行方案，会主动指出风险与更优解。
- 重要改动先讨论方案再动刀（"先讨论磨方案，不着急动刀子"），小修复可直接做。
- 用户授权：执行代码不需要批准，但**不做毁灭性动作**（删除、重置等需确认）。

## 三、技术要点与踩坑记录

### 打包 / 发布
- **electron-builder 图标不生效的根因**：`signAndEditExecutable: false` 会连 exe 图标写入一起跳过。正确做法是 `signExecutable: false`（只跳过代码签名、保留图标与元数据）。日志出现 "executable resource editing and code signing skipped" 即图标被跳过。
- **无边框窗口最大化盖任务栏**：系统最大化会向外越界约 7px 且 Windows 锁定边界（setBounds 无效）。方案：手动"伪最大化"——点击最大化按钮时 `setBounds(workArea)`，精确贴住工作区。
- **GitHub Actions 工作流三个坑**：
  1. PowerShell 里 `-c.publish.provider=github` 会被解析成配置文件路径 → 改为在 `electron-builder.yml` 配置 publish，工作流只跑 `npx electron-builder --publish always`。
  2. 必须先 `npm run build`（dist/dist-electron 被 .gitignore 排除，不构建则入口文件缺失）。
  3. 发布需要 `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`，且仓库 Settings → Actions → Workflow permissions 需设为 **Read and write**。
- **本地打包 GitHub 下载 electron 超时**：设置镜像 `$env:ELECTRON_MIRROR='https://npmmirror.com/mirrors/electron/'`。
- **Actions 偶发"exe 上传失败"但 run 显示 success**：发布后务必用 `gh release view <tag> --json assets` 核对 exe 是否真的上传；缺失时手动 `gh release upload` 补（注意文件名空格会被替换成点，需用无空格副本上传）。
- **Release 默认是草稿**：electron-builder 创建的 release 是 `draft: true`，需 `gh release edit <tag> --draft=false` 公开。

### Git / 平台
- **Gitee 私人令牌**：用完提醒重置，但频繁重置会导致每次同步都要新令牌。建议生成后长期保留，仅在泄露时更换。
- **Gitee API 限制**：不能用 API 修改仓库描述（405），需网页操作；Release 附件单文件限 100MB（安装包 127MB+ 需 7z 分卷 `-v70m`）。
- **GitHub 用户级 GH_TOKEN 是只读**：会覆盖 gh 的完整权限账号（OAuth）。push 前先 `Remove-Item Env:GH_TOKEN`，并 `gh auth setup-git`。
- **PowerShell → Python 管道中文乱码**：`@'...'@ | python -` 会以 GBK 传 stdin 导致中文变 `?`。改文件用 PowerShell 直接处理或写 .py 文件再执行。

### 前端 / 交互
- **全局快捷键冲突**：AppShell 的"1-9 切导航"会吞掉复习评级按键。解决：CardsPage 用 `window.addEventListener('keydown', fn, true)`（捕获阶段）+ `stopImmediatePropagation()`。
- **mock preload 测试**：端到端测试用 mock preload（`E:\tmp\...preload.cjs`），需 `sandbox: false` 才能 require('fs')；`getDailyTasks` 要支持 date 参数否则"昨日遗留"区会串数据。
- **任务联动**：跨页面状态同步靠 `bumpDataVersion()`（AppContext）触发各页面/Context 的 useEffect 重新拉取。

## 四、质量保障（每次发布前必跑）

```
npm run typecheck      # TS 类型
npm run build          # 主进程 tsc + 前端 vite
npm run smoke          # 数据层冒烟（50 项）
npm run test           # 单元测试（13 项）
node node_modules\electron\cli.js 'E:\tmp\reader-test\test-main.cjs'   # 端到端（68 项）
```
另加：针对当轮改动的专项 UI 测试（mock preload + executeJavaScript 驱动）。

## 五、发布流程（三平台）

1. 本地打包 `npm run package`（镜像 + `CSC_IDENTITY_AUTO_DISCOVERY=false`）→ 生成 `release\Study desktop Setup X.Y.Z.exe`。
2. Git 提交 + `git tag vX.Y.Z` + push GitHub → Actions 自动构建发布 → `gh release edit --draft=false` 公开 → **核对 exe asset**。
3. Gitee：`git push .../study-desktop.git main:master` + 7z 分卷 + API 创建 Release + 上传分卷（用有效令牌）。
4. 更新 README 下载链接（GitHub latest / 加速 / Gitee 分卷 / 百度网盘）→ 同步两平台。
5. 提醒用户百度网盘上传新安装包并给新链接。

## 六、迭代节奏建议

- 每个版本聚焦 3-5 个真实痛点，做完即发，避免憋大招。
- 发布后让用户实际用几天再进入下一轮（收集手感反馈）。
- 功能纵深与"精修"交替进行：先补功能，再回头统一视觉与交互细节。
